## 1. 结论与目标

本阶段恢复 Clade 后端自动化测试的历史红线，不改变现有模拟规则、接口结构、存档格式或前端交互。处理原则是以当前已经落地的产品设计为准，修正仍在验证旧行为的测试；只有运行时验证能够证明产品代码确有缺陷时，才考虑最小产品代码改动。

实施第 1 批时，插件注册隔离修复后稳定暴露出血统插件索引始终返回 0 的真实缺陷。用户已于 2026-07-14 确认扩大范围：允许修复 `AncestryEmbeddingPlugin.build_index()` 的索引流程，并把遗传惯性测试改为通过真实索引流程准备状态。该例外不授权修改其他产品代码。

目标结果为：后端当前收集到的 556 项测试中，554 项通过、0 项失败、0 项初始化错误，保留 2 项 Windows 符号链接限制导致的预期跳过。

## 3. 范围与非目标

### 3.1 本阶段包含

- 修复五个历史测试文件中已经确认的过期断言和测试隔离问题。
- 为插件注册表建立明确、可重复、不会依赖 Python 模块导入缓存的测试夹具。
- 修复血统插件在向量生成前过滤所有候选、导致索引始终为空的问题。
- 让遗传惯性测试通过公开的 `build_index()` 流程积累历史并建立缓存。
- 让配置、兼容占位类和模拟流水线测试验证当前真实契约。
- 将受 float32 表示误差影响的精确断言改成边界明确的近似比较。
- 每一类修复独立验证、独立提交，最后执行完整后端和前端门禁。

### 3.2 本阶段不包含

- 不改变生态、死亡率、杂交、生态位或其他模拟计算规则。
- 不恢复已经淘汰的 `preliminary_mortality` 阶段。
- 不把 `TileBasedMortalityEngine` 恢复成实际计算引擎，也不恢复它的旧警告行为。
- 不改变 `ConfigService` 当前读取默认配置的语义。
- 不通过删除测试、跳过测试、捕获所有异常或放宽成无意义断言来获得绿色结果。
- 不集中清理已有的 45 条测试警告。
- 不修改主工作区中的用户文件，不合并到 `main`，也不推送远端。

## 4. 方案选择

采用“以当前产品契约为准，优先修正测试”的方案。

没有采用恢复旧产品行为的方案，因为旧阶段、旧警告和对象身份要求已经不再代表当前架构；恢复它们会把淘汰逻辑重新带回产品。也不采用直接跳过或删除失败测试的方案，因为那会降低保护能力，无法证明当前行为可靠。

产品代码改动设置单独门槛：仅凭现有测试的模块缓存问题，不修改运行时代码。插件隔离后新增的 2 个稳定失败已经证明血统索引存在真实缺陷，且用户已确认最小修复；后续如出现其他产品缺陷，仍须停止当前批次、记录证据并重新确认范围。

## 5. 详细设计

### 5.1 第一批：Embedding 插件测试隔离

#### 当前问题

`PluginRegistry.clear()` 会清空插件注册信息。随后执行 `from .. import behavior_strategy` 等导入时，如果模块此前已经加载，Python 会直接返回缓存模块，不会再次运行 `@register_plugin(...)` 装饰器。因此 `get_instance()` 返回 `None`。这属于测试之间共享全局状态后没有正确恢复，不是插件算法失败。

#### 处理方式

- 在插件测试文件中增加统一夹具，集中维护内置插件名与具体插件类的对应关系。
- 夹具在每个相关测试开始前先清理注册表，再通过 `PluginRegistry.register(name, plugin_class)` 显式注册所需插件。
- 测试结束后再次清理注册表，避免当前测试污染后续测试。
- 类级测试和降级路径测试都使用同一套注册方式，不再依赖“再次 import 会触发装饰器”的隐含假设。
- 不使用 `importlib.reload()` 作为常规修复，因为重载会重新创建类对象并扩大模块级副作用，使测试更难预测。
- 保留插件的初始化、索引、搜索、降级路径和统计断言，修复注册前置条件而不是削弱功能验证。

#### 运行时保护

实现时增加或复用一个最小验证，证明全新 Python 进程按正常应用导入顺序能够发现内置插件。若该验证失败，说明存在真实启动缺陷，应暂停并重新确定产品代码修复范围；若验证通过，则本批只改测试。

#### 已确认的血统索引例外

显式注册完成后，血统插件的两个测试不再被初始化错误遮住。修复方式限定为：

- `build_index()` 先接收 `_compute_ancestry_vector()` 生成的血统记录，构建文本并调用 embedding；向量生成后再写回血统缓存。不能在 embedding 之前用空占位向量过滤记录。
- 遗传惯性测试不再直接写入旧的 `_trait_history` 后立即调用预测，而是多次通过 `build_index()` 使用稳定性状建立当前 `_ancestry_cache`，再验证高惯性与稳定趋势。
- 不改变遗传惯性公式、阈值、返回字段、插件注册接口或其他插件实现。

### 5.2 第二批：配置与兼容占位契约

#### 默认 UI 配置

当配置文件不存在时，`ConfigService.get_ui_config()` 当前返回内容相同但相互独立的默认 `UIConfig`。旧测试用 `config1 is config2` 要求两个结果必须是同一个对象，这把内部对象身份误当成了产品契约。

调整后的测试验证：

- 两次读取都得到有效的默认配置；
- 配置内容相等；
- 不再要求对象身份相同；
- 测试名称和说明准确表达“默认配置读取语义”，不再宣称验证缓存身份。

这可以避免调用方意外修改共享默认对象，同时不改变配置文件存在时的实际读取逻辑。

#### `TileBasedMortalityEngine` 兼容占位类

该类已经是 GPU-only 架构下的兼容入口，实际死亡率计算由 `TensorEcologyStage` 完成。测试应验证它仍可被旧调用方安全构造，并符合占位类当前公开行为；不再要求未注入旧配置时必须写出“未注入”或“使用默认值”警告。

本批不重新加入旧警告、不恢复旧配置依赖，也不把计算职责移回兼容类。

### 5.3 第三批：模拟流水线阶段契约

#### 生态现实阶段依赖

`EcologicalRealismStage` 当前依赖的是规范阶段显示名：

```text
获取物种列表
物种分层与生态位
```

测试将按当前依赖集合验证，不再要求旧标识 `fetch_species`。断言保留集合精确性，避免只检查“非空”而漏掉依赖错误。

#### 阶段注册表

阶段注册表测试将移除对已淘汰 `preliminary_mortality` 的要求，并继续逐项验证当前仍应存在的核心阶段。不能为了兼容旧测试而注册一个无实际用途的空阶段。

若实现过程中发现当前代码、阶段文档和真实默认流水线三者不一致，应先确定哪一项是设计真相；该冲突会明显扩大范围，因此暂停并重新确认。

### 5.4 第四批：张量浮点断言

只修改已确认受 float32 表示误差影响的 `0.1` 精确比较，使用 `pytest.approx(0.1, abs=1e-6)` 或等价的明确容差。该容差远小于业务阈值，足以容纳 float32 表示误差，但不会掩盖算法把最小重叠因子计算成其他值的错误。

矩阵对称性、共享地块数量、对角线和大于阈值等其他断言继续保留。不得把整个文件改成宽泛的近似比较，也不得通过四舍五入产品输出改变计算结果。

## 6. 状态、数据与错误边界

本阶段不改变业务数据流、API、数据库或存档。唯一需要管理的共享状态是测试进程内的插件注册表：测试开始时建立已知状态，测试结束时清空，从而使测试顺序不影响结果。

测试应继续让真实错误直接失败，不增加吞异常、静默降级或通用 `try/except`。配置和流水线批次只更新对当前契约的描述与断言；张量批次只处理表示误差，不改变异常路径或返回数据。

## 7. 实施与提交顺序

按照以下四个独立批次执行，每批都先运行对应失败测试，确认它能针对预期根因失败；修改后复跑该文件或最小相关集合，并形成单独提交：

1. 插件注册表测试隔离与已确认的血统索引最小修复。
2. 配置读取与兼容占位契约。
3. 模拟流水线阶段契约。
4. 张量 float32 近似断言。

每批完成后检查差异，确认没有顺带修改产品行为。四批完成后再执行完整门禁。这样任何批次都能单独审阅和回退，也能快速定位回归来源。

## 9. 风险与暂停条件

- **插件真实启动缺陷：** 如果全新进程的正常导入也无法发现内置插件，暂停并提交运行时证据；已确认的血统索引缺陷只允许按第 5.1 节处理。
- **契约来源冲突：** 如果代码、设计文档和实际默认流水线对阶段名称或职责定义不一致，暂停并确认产品真相。
- **断言过度放宽：** 近似比较必须限定在 float32 表示误差级别；若真实偏差更大，应按算法问题处理。
- **测试数量漂移：** 如果完整测试不再收集 556 项，先查明收集差异，不能只以“全绿”作为通过依据。
- **范围外失败：** 如出现新的产品代码失败、数据迁移或接口改动需求，不在本阶段顺手处理，应重新确认。
