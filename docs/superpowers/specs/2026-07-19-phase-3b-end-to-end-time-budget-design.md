# Phase 3B 端到端时间预算与流式终止语义设计

## 1. 背景

Phase 2C 已让连接测试、模型列表、`ModelRouter` 的运行时网络入口和 `EmbeddingService` 的远程批次经过统一安全出口，并加入 DNS 审批、固定目标 IP、分阶段超时、响应大小限制、取消传播和资源清理。Phase 3A 又修复了运行时凭据快照和缓存身份边界。

当前剩余问题是：用户配置的 `timeout` 仍主要作为 HTTP 读取阶段的时限使用，尚未形成一次逻辑 AI 请求的端到端总预算。DNS、等待并发名额、多个已审批 IP 依次建连、写入、读取、自动重试和退避分别计时后，用户实际等待时间可能明显超过设置值。流式入口、流式辅助工具和报告生成器还存在 20、30、60、120 和 600 秒等多层计时，终止语义相互重叠。

因此，Phase 3B 要让超时设置与用户实际感知一致，同时保留流式生成“持续输出就继续”的产品体验。

## 2. 目标

1. 普通 AI 请求使用一个端到端总时间预算，从入口被调用开始计时。
2. 排队、DNS、候选 IP 建连、发送、读取、重试退避和后续尝试共享同一预算。
3. 配置为 60 秒时，一次普通逻辑请求不能因为三次重试变成 180 秒以上。
4. 流式请求把配置的 `timeout` 解释为空闲时限；持续收到真实 AI 内容时可以继续，但从入口开始最多运行 600 秒。
5. 流式中途超时时保留已展示的内容，同时明确标记为中断；残缺结构不得作为完整业务结果。
6. 主动取消继续向调用方传播，不能伪装成超时或普通错误。
7. 同步、异步、普通、流式和 Embedding 远程调用使用一致、可测试的计时基础设施。
8. 保留 Phase 2C 的 URL、DNS、代理、重定向、响应限制、错误脱敏和资源清理边界。

## 3. 非目标

- 不改变数据库结构、存档格式、游戏规则或模拟结果。
- 不改变现有 AI 服务商选择、负载均衡算法、重试次数或退避公式。
- 不增加新的用户设置；普通请求总时限和流式空闲时限继续复用现有 `timeout`。
- 不改变连接测试 10 秒、模型列表 15 秒的现有产品合同；若抽取共享基础设施，只做等价迁移。
- 不重写 HTTP 客户端或 Phase 2C 的 DNS 固定传输架构。
- 不把流式心跳、连接状态或空 SSE 行当作 AI 内容。
- 不在本阶段解决与时间预算无关的报告生成质量或前端视觉改版。

## 4. 已确认的产品决定

### 4.1 普通请求

- `timeout=60` 表示从逻辑请求入口开始到完整结果可用，总共最多 60 秒。
- 内部排队也计入 60 秒。
- 同一逻辑请求的所有自动重试和退避共享这 60 秒。
- DNS、多个候选 IP、连接、写入、读取和解析都不能重新获得完整预算。

### 4.2 流式请求

- `timeout=60` 表示连续 60 秒没有收到真实 AI 内容即为空闲超时。
- 排队和等待第一段真实内容属于初始空闲期。
- 每收到一段真实内容，下一次等待上游内容时重新获得一个完整的空闲窗口。
- 内部连接状态、心跳、注释行和空数据不能重置空闲计时。
- 即使持续输出，从请求入口开始也最多运行 600 秒。
- 流式入口不自动重试，避免部分内容已展示后重新生成重复内容。

### 4.3 部分结果

- 已经展示给用户的流式文字保留。
- 中断后不得发送成功完成状态。
- 需要完整 JSON 或完整结构的业务流程必须使用现有规则降级，不得解析或保存残缺结构。
- 最终持久化的业务结果必须是完整结果或完整降级结果；已展示的部分文字只作为本次交互痕迹。

## 5. 方案选择

### 5.1 采用：统一绝对截止时间

在逻辑入口创建基于单调时钟的时间预算，并把同一个绝对截止时间传递给排队、重试和安全网络层。每个阶段实际可用时长为：

```text
min(该阶段原有安全上限, 整次请求剩余时间)
```

绝对截止时间不会因重试或进入下一阶段而重置，也不受系统墙上时钟调整影响。

### 5.2 不采用：仅在最外层包装超时

只在路由外层使用 `wait_for` 虽然改动较少，但同步 DNS 或后台网络操作可能在调用方返回后继续运行，底层阶段也无法知道剩余预算，不足以保证资源上限和多 IP 行为。

### 5.3 不采用：重写网络栈

全面更换 HTTP 和 DNS 架构会扩大 Phase 3B 范围，并增加破坏 Phase 2C 已验证安全属性的风险。

## 6. 架构

### 6.1 `DeadlineBudget`

新增独立的小型时间预算组件，职责仅包括：

- 记录入口开始时间和绝对截止时间；
- 使用可注入的单调时钟计算剩余时间；
- 判断预算是否耗尽；
- 为某一阶段返回 `min(阶段上限, 剩余时间)`；
- 在预算耗尽时产生统一的 `outbound_timeout`。

预算对象不读取全局配置、不发送网络请求、不决定重试次数，也不记录日志。这样可以使用假时钟进行快速、稳定的单元测试。

普通请求只创建一个 `DeadlineBudget`。入口应在执行配置准备前记录 `started_at`，待解析出有效 `timeout` 后以 `started_at + timeout` 建立绝对截止时间，从而让本地准备工作也不能隐性延长用户等待。

### 6.2 有界阻塞操作执行器

系统 DNS 解析等阻塞调用无法由 Python 安全强杀。Phase 3B 将现有连接测试使用的有界 daemon worker 机制抽取为共享安全组件，并提供同步和异步等待接口：

- 同时遗留的阻塞任务最多 4 个；
- 调用方只等待当前预算的剩余时间；
- 到期后及时返回 `outbound_timeout`；
- 未退出的系统调用继续占用原槽位，直到自行结束；
- 槽位耗尽时，后续请求同样在自己的剩余预算内等待，不创建无限线程；
- worker 异常映射为固定错误，不向日志或响应暴露底层异常内容。

连接测试和模型列表保持现有 10/15 秒合同；共享执行器抽取不能改变其返回结构或安全行为。

### 6.3 安全网络层

`SafeRuntimeClient` 的普通同步和异步 JSON 入口接收调用方创建的 `DeadlineBudget`，不再把 `read_timeout` 当作整次请求的唯一时间概念。

一次普通调用按以下顺序使用同一预算：

1. URL 语法规范化；
2. 有界 DNS 解析和地址策略审批；
3. 创建固定 IP 传输；
4. 连接、TLS、写入和读取；
5. 响应大小检查、解码和 JSON 对象解析；
6. 关闭响应、客户端、传输和连接池。

HTTPX/httpcore 的阶段时限继续保留，但每次传入底层的值都要被剩余预算收紧。多 IP 建连循环在尝试每个地址前重新计算剩余时间；不得为每个 IP 重置完整的 10 秒连接上限。预算耗尽统一映射为 `outbound_timeout`。

同步入口使用有界执行机制保证调用方按截止时间返回。异步入口对阻塞 DNS 使用异步等待的有界 worker，对异步网络阶段使用绝对截止时间保护；取消时立即传播 `asyncio.CancelledError`。

### 6.4 `ModelRouter` 普通调用

以下运行时入口全部使用统一预算：

- `invoke()`；
- `ainvoke()`；
- `call_capability()`；
- `acall_capability()`；
- `chat()`。

异步入口在等待并发 semaphore 前已经拥有预算。取得名额时使用剩余时间；若排队耗尽预算，直接返回或抛出现有入口约定的脱敏超时结果。

`ainvoke()` 的多次尝试共享一个预算：

- 只有 `outbound_connect_failed` 和 `outbound_timeout` 保留现有重试资格；
- 重试退避只能睡眠到剩余预算为止；
- 退避后没有剩余时间时，不再开始下一次 DNS 或连接；
- 最终预算耗尽只统计一次逻辑请求超时，单次尝试可保留内部诊断计数，但不能重复增加用户侧请求总数；
- 安全错误、响应过大、编码或结构错误继续立即停止且不重试。

### 6.5 Embedding 远程批次

每个远程 Embedding 逻辑批次在第一次尝试前创建一个预算。该批次的 DNS、连接、读取、最多三次既有尝试和退避共享 `EmbeddingService.timeout` 对应的总预算。

保持 Phase 2C 已确认的降级规则：只有连接失败或超时重试耗尽，并且调用开始时已经满足 `require_real=false` 与 `allow_fake_embeddings=true`，才允许生成不可缓存的远程失败假向量。安全或响应错误仍不得生成假向量。

多个独立批次各自拥有预算；Phase 3B 不把整个大型 Embedding 作业强行压缩进单个批次时限，也不改变批次大小和并行策略。

### 6.6 流式预算

流式入口使用一个最终绝对边界和分段的上游空闲窗口：

- `hard_deadline`：入口开始时间加 600 秒。
- `initial_idle_deadline`：入口开始时间加配置 `timeout`，只负责限制排队、DNS、建连和首段真实内容。
- 首段内容之后：每次开始等待下一段上游内容时，最多等待配置的 `timeout`，同时仍受 `hard_deadline` 剩余时间约束。

等待 semaphore、DNS、建连和第一段真实内容时，同时受 `initial_idle_deadline` 和 `hard_deadline` 约束。收到非空的真实模型内容后，下一次对上游 `__anext__()` 的实际等待时间为配置空闲时限与 hard 剩余值中的较小者。

路由或业务调用方处理已经交付内容所花的本地时间不属于“等待上游输出”，因此不触发空闲超时；但它始终消耗 600 秒最终总时长。若上游内容已经进入缓冲区，调用方恢复读取时应立即取得内容，而不是被本地处理耗时误判为 AI 卡住。

以下内容不能刷新空闲时间：

- `connecting`、`connected`、`receiving` 等本地状态事件；
- UI 或服务端心跳；
- SSE 注释行；
- 空行、空字符串或只包含协议控制信息的事件；
- 调用方处理一段已交付内容后自行生成的状态或心跳。

最终 600 秒上限从入口开始，包含排队，不因收到内容而延长。

## 7. 流式终止合同

### 7.1 终止状态

一条流只允许出现一个终止结果：

| 结果 | 条件 | 业务含义 |
|---|---|---|
| `completed` | 上游正常结束且协议完整 | 内容可作为完整结果 |
| `interrupted` | 已产生真实内容后空闲或总时限耗尽 | 保留展示内容，但业务结果必须降级 |
| `error` | 首段内容前超时，或发生安全/协议/响应错误 | 没有可用的完整 AI 结果 |
| `cancelled` | 调用方主动取消 | 由取消所有者发布状态，底层继续抛出取消 |

`completed` 与 `interrupted`/`error` 互斥。发生中断后不能再补发完成事件。

### 7.2 结构化事件

路由层在已经输出内容后遇到超时时，发出脱敏的 `interrupted` 状态，包含稳定原因码 `outbound_timeout` 和 `partial=true`，不包含上游异常、完整 URL、请求体或响应体。

若尚未输出真实内容，则沿用错误事件，固定公开消息为“外部服务请求超时”。安全拦截和响应错误继续使用 Phase 2C 的固定代码和公开消息。

底层在收到 `asyncio.CancelledError` 时不得转换为错误事件或超时。最接近用户操作、且拥有取消动作的上层负责发布 `cancelled`，随后让取消继续传播。

### 7.3 业务消费

流式辅助工具以内部 `StreamOutcome` 表达结果：

- `content`：已收到的文本；
- `completed`：是否完整结束；
- `reason`：稳定终止原因码或空值。

现有调用方迁移到这个明确合同：

- 展示回调已经发送的文字不撤回；
- 只有 `completed=true` 才能解析 JSON 或作为完整 AI 业务结果；
- `completed=false` 时报告、分析和模拟逻辑使用现有完整降级结果；
- 最终保存内容不能使用残缺 JSON 或把部分报告标记为完整 AI 报告；
- 前端进度层接收 `ai_stream_interrupted`，显示“AI 生成中断，已使用备用结果”的警告状态。

## 8. 资源清理与取消

- 同步和异步响应、客户端、传输和连接池在成功、错误、超时、取消、调用方提前停止和解析失败时都关闭一次。
- 异步 generator 的 `aclose()` 继续关闭其拥有的响应和客户端。
- 清理阶段的次要异常不能覆盖主要超时、错误或取消。
- 主动取消不得增加超时统计，不触发普通重试，也不生成假向量。
- 已超时但仍阻塞在操作系统 DNS 中的 worker 不再接触调用方状态；它只保留原槽位并在自行退出后释放。
- 任何后台任务都不能在超时后写入缓存、发布成功事件或更新服务商成功延迟。

## 9. 统计与日志

- 以一次逻辑请求为单位记录总时长、成功、超时和错误。
- 排队耗时计入逻辑请求总时长。
- 可在内部调试日志记录尝试序号、固定错误码、阶段和剩余预算，但不得记录完整目标 URL、查询参数、API Key、Authorization 头、请求正文或上游响应正文。
- 流式 `interrupted` 计为超时而不是成功；保留的展示文字不改变统计结果。
- 用户取消单独记录为取消，不计入超时率。
- Embedding 远程失败后产生的不可缓存假向量不能更新远程服务成功和延迟统计。

## 10. 预计代码范围

实现计划可在保持职责边界的前提下微调文件名，预计涉及：

| 区域 | 预计文件 | 作用 |
|---|---|---|
| 时间基础设施 | `backend/app/security/deadline.py`（新增）及测试 | 单调时钟预算、阶段剩余值 |
| 有界阻塞执行 | `backend/app/security/safe_http.py` 或抽取的共享模块 | 复用同步/异步有界 worker |
| URL 与固定传输 | `backend/app/security/outbound_url.py`、`pinned_transport.py` | DNS 和多 IP 共享剩余预算 |
| 运行时 HTTP | `backend/app/security/runtime_http.py` | 普通总预算、流式双截止时间、清理 |
| AI 路由 | `backend/app/ai/model_router.py` | 排队、重试和终止事件 |
| 流式辅助 | `backend/app/ai/streaming_helper.py` | `StreamOutcome` 和统一事件桥接 |
| Embedding | `backend/app/services/system/embedding.py` | 每个远程逻辑批次共享预算 |
| 报告调用方 | `backend/app/services/analytics/report_builder.py`、`report_builder_v2.py` 等实际调用方 | 移除冲突计时并拒绝残缺业务结果 |

不允许借 Phase 3B 进行无关的 `ModelRouter` 大规模拆分或报告模块重写。

## 11. 测试设计

所有测试使用假时钟、假 resolver、记录型 network backend 或本机内存对象，不访问真实公网和真实 AI 服务。

### 11.1 时间预算单元测试

- 正常计算剩余时间；
- 阶段上限小于剩余预算时使用阶段上限；
- 剩余预算更小时使用剩余值；
- 单调时钟推进到截止点时固定超时；
- 系统墙上时钟变化不影响预算；
- 非法、非有限、布尔或非正 timeout 在网络前被拒绝。

### 11.2 DNS 与多 IP

- DNS 阻塞超过毫秒级测试预算时，调用方快速得到 `outbound_timeout`；
- 最多 4 个遗留阻塞 worker，不能无限创建线程；
- 多个候选 IP 的失败尝试依次消耗同一预算；
- 后续 IP 没有剩余时间时不再调用 `connect_tcp()`；
- Host、SNI、证书主机名和 Phase 2C 的固定 IP 语义保持不变。

### 11.3 普通同步与异步请求

- DNS、连接、写入和完整正文读取共享一个总预算；
- 大小限制和解析发生在截止时间内；
- 同步和异步入口使用相同公开错误码；
- 到期后连接、响应和客户端准确关闭；
- 异步取消原样传播且不映射为超时。

### 11.4 排队与重试

- 例如 20 毫秒排队加 40 毫秒网络不能突破 60 毫秒总预算；
- 第一次尝试消耗 40 毫秒后，第二次只能使用剩余约 20 毫秒；
- 退避也消耗剩余预算；
- 预算耗尽后不再 DNS、不再建连、不再睡眠；
- 安全和响应错误仍只调用一次；
- 超时统计以逻辑请求为单位，不因多次尝试重复计算。

### 11.5 流式请求

- 排队和等待首个真实内容受初始空闲时限约束；
- 状态、心跳、空 SSE 行不能刷新空闲时限；
- 真实内容片段刷新空闲时限；
- 调用方处理已交付内容超过空闲配置值、但未超过 hard 上限时，不能仅因本地耗时产生 AI 空闲超时；
- 持续输出可以超过配置的 60 秒语义；
- 无论是否持续输出，600 秒硬上限都从入口开始且不重置；
- 有部分内容后超时只产生 `interrupted`，不产生 `completed`；
- 无内容超时产生 `error`；
- 主动取消由上层标记 `cancelled`，底层仍抛出取消；
- 提前 `aclose()` 和清理异常不覆盖主要终止原因。

### 11.6 业务与前端

- `StreamOutcome.completed=false` 时不解析残缺 JSON；
- 部分展示内容保留，但报告和结构化分析使用完整降级结果；
- `ai_stream_interrupted` 在进度界面显示警告，不显示成功；
- 现有 `completed`、普通错误和取消显示保持兼容；

## 13. 风险与缓解

### 13.1 系统繁忙时更早超时

排队现在计入预算，繁忙情况下请求可能比以前更早进入降级。这是总等待时间可预测的预期结果。现有并发设置仍可由用户调整，Phase 3B 不自动提高并发。

### 13.2 慢服务暴露真实时限

普通请求不再因重试隐性延长，慢服务更可能按配置超时。用户可以通过现有设置主动提高 timeout；系统不能偷偷扩大它。

### 13.3 操作系统 DNS 无法强杀

调用方能按时返回，但底层 DNS 线程可能暂时存在。有界四槽执行器确保残留数量固定，任务结束后释放槽位，且过期任务不能写入业务状态。

### 13.4 旧调用方误用部分内容

通过 `StreamOutcome` 和终止状态测试逐一迁移现有调用方；只有明确的 `completed=true` 才能进入解析和持久化路径。

### 13.5 重复计时器遗漏

实施时对 `asyncio.wait_for`、`asyncio.timeout`、`chunk_timeout`、`idle_timeout` 和硬编码 20/30/60/90/120/600 进行调用点清单审计。只删除与统一预算重复的计时，保留与非 AI 业务相关的独立时限。

## 14. 实施顺序建议

1. 先以测试定义 `DeadlineBudget` 和有界阻塞执行合同；
2. 让运行时 HTTP 的同步、异步普通请求接受并执行预算；
3. 让固定传输的多 IP 建连共享剩余时间；
4. 迁移 `ModelRouter` 的普通入口、排队和重试；
5. 迁移 Embedding 远程批次；
6. 实现流式双截止时间与结构化终止状态；
7. 迁移流式辅助工具、报告调用方和前端提示；
8. 更新文档并执行完整质量门与安全复审。

每一步遵循红—绿—重构：先写能证明旧行为不符合合同的失败测试，再进行最小实现，最后运行相关回归测试。
